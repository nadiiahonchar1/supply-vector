# SupplyVector

SupplyVector — система управління запасами та розподіленою логістикою торговельної мережі.

Проєкт призначений для мережі магазинів, у якій окремі магазини можуть виконувати не лише роль точок продажу, а й роль локальних складських приміщень для інших магазинів мережі.

Головна ідея системи — бачити всю мережу як єдину розподілену систему запасів і приймати логістичні рішення на основі фактичної потреби, доступних залишків, відстаней, транспорту, часу та вартості перевезень.

---

## 1. Концепція

Початкова модель SupplyVector передбачала централізовану логістику з окремими логістичними центрами.

Оновлена концепція відмовляється від обов'язкової залежності від логістичних центрів.

У межах мережі:

- магазин може бути кінцевою точкою продажу;
- магазин може одночасно зберігати запас;
- магазин може виступати джерелом товару для іншого магазину;
- товар може переміщуватися безпосередньо між магазинами;
- мережа розглядається як набір взаємопов'язаних складських вузлів;
- логістика визначає, звідки доцільніше перемістити товар і яким транспортом.

Таким чином, SupplyVector працює як система **розподіленого управління запасами та логістикою**.

---

# 2. Основні цілі

Система повинна допомагати:

1. контролювати залишки товарів;
2. визначати дефіцит і надлишок;
3. бачити запаси по всій мережі;
4. використовувати магазини як розподілені складські вузли;
5. знаходити оптимальне джерело товару;
6. формувати переміщення товарів між магазинами;
7. об'єднувати переміщення у вантажні рейси;
8. оптимізувати завантаження транспортних засобів;
9. мінімізувати порожні рейси;
10. не допускати надмірного очікування заради повного завантаження;
11. враховувати терміновість потреби;
12. враховувати відстань, час та вартість доставки;
13. зберігати історію логістичних рішень;
14. надавати оператору зрозумілі рекомендації, а не лише сирі дані.

---

# 3. Ключова логістична проблема

Головна задача SupplyVector — знайти баланс між двома крайнощами:

### Порожній або майже порожній транспорт

Машина вирушає занадто рано.

Наслідки:

- низьке використання місткості;
- висока вартість одиниці перевезеного товару;
- зайві рейси.

### Надмірне очікування

Система чекає, поки накопичиться достатня кількість товару для повного завантаження.

Наслідки:

- товар довго очікує;
- магазин може залишитися без потрібного запасу;
- порушуються терміни поповнення;
- повна машина вже не компенсує втрати від затримки.

Тому система не повинна оптимізувати лише відсоток завантаження.

Вона повинна оптимізувати **загальну логістичну ефективність**.

---

# 4. Принцип оптимізації транспорту

Для кожного потенційного рейсу система повинна оцінювати декілька факторів:

- обсяг вантажу;
- вагу вантажу;
- доступну місткість автомобіля;
- кількість товарних позицій;
- терміновість;
- час до виникнення дефіциту;
- відстань;
- орієнтовний час доставки;
- вартість рейсу;
- вартість очікування;
- вартість потенційного дефіциту;
- можливість об'єднання кількох переміщень;
- можливість використати інший складський вузол.

У загальному вигляді рішення можна представити як мінімізацію:

```text
Total Cost =
    Transport Cost
  + Waiting Cost
  + Stockout Risk Cost
  + Underutilization Cost
```

При цьому система повинна мати можливість відправити неповністю завантажений автомобіль, якщо очікування додаткового вантажу стає дорожчим за недовантаження.

---

# 5. Динамічне формування рейсів

Рейс не повинен створюватися лише один раз на основі поточних замовлень.

Система повинна працювати динамічно.

При появі нового переміщення:

1. перевірити існуючі заплановані рейси;
2. перевірити напрямок;
3. перевірити доступну місткість;
4. перевірити час відправлення;
5. перевірити терміновість нового переміщення;
6. визначити, чи можна додати вантаж до існуючого рейсу;
7. порівняти це з альтернативою окремого рейсу;
8. прийняти рішення.

---

# 6. Часове вікно

Для кожного переміщення потрібно визначати:

- `earliestDelivery` — найраніший допустимий час доставки;
- `latestDelivery` — крайній допустимий час доставки;
- `priority` — пріоритет;
- `createdAt` — час створення потреби.

Це дозволяє системі не чекати нескінченно.

Наприклад:

```text
Потреба A:
доставка бажана протягом 2 днів

Потреба B:
доставка бажана протягом 7 днів

Потреба C:
доставка критична сьогодні
```

Система може об'єднати A і B в один рейс, але C не повинна чекати B.

---

# 7. Розподілені складські вузли

Кожен магазин може мати складські характеристики:

- доступну площу;
- максимальну місткість;
- поточне завантаження;
- дозволені категорії товарів;
- доступний товар;
- мінімальний запас;
- максимальний запас;
- резервований товар.

Магазин стає логістичним вузлом:

```text
Store
 ├── Sales
 ├── Inventory
 ├── Storage
 ├── Incoming Shipments
 └── Outgoing Shipments
```

---

# 8. Джерело товару

Коли магазин потребує товар, система не повинна автоматично шукати лише один центральний склад.

Вона повинна розглянути доступні джерела:

```text
Store A
Store B
Store C
Store D
```

Для кожного джерела оцінюються:

- доступна кількість;
- надлишок;
- мінімальний запас джерела;
- відстань;
- транспортна доступність;
- час доставки;
- вартість;
- пріоритет джерела.

Після цього формується рейтинг джерел.

---

# 9. Запас, який можна переміщувати

Не весь доступний залишок магазину можна використовувати для логістики.

Потрібно враховувати:

```text
AvailableForTransfer =
    CurrentQuantity
  - ReservedQuantity
  - SafetyStock
```

Таким чином, магазин не повинен віддати товар, який необхідний йому самому для підтримання мінімального запасу.

---

# 10. Логіка дефіциту

Для кожного товару система повинна визначати:

- поточний запас;
- мінімальний запас;
- цільовий запас;
- прогнозоване споживання;
- очікувані надходження;
- резерв;
- прогнозований дефіцит.

Базова модель:

```text
ProjectedStock =
    CurrentStock
  + Incoming
  - Reserved
  - ExpectedConsumption
```

Якщо прогнозований запас опускається нижче допустимого рівня, формується потреба на поповнення.

---

# 11. Пріоритет переміщень

Кожне переміщення повинно отримувати пріоритет.

Наприклад:

```text
CRITICAL
HIGH
NORMAL
LOW
```

Пріоритет може залежати від:

- ризику stockout;
- кількості днів до дефіциту;
- важливості магазину;
- важливості товару;
- кількості доступного товару;
- часу доставки.

---

# 12. Логістичний граф

Мережу можна представити як граф:

```text
          Store B
         /       \
        /         \
Store A -------- Store C
        \         /
         \       /
          Store D
```

Де:

- вершини — магазини;
- ребра — можливі маршрути;
- вага ребра — відстань, час або вартість;
- потік — переміщення товару.

У майбутньому це дозволить реалізувати:

- пошук найкоротшого маршруту;
- пошук найдешевшого маршруту;
- багатоточкові маршрути;
- consolidation;
- cross-store transfers.

---

# 13. Транспорт

Транспортний засіб повинен мати параметри:

```text
Vehicle
 ├── id
 ├── name
 ├── type
 ├── capacityWeight
 ├── capacityVolume
 ├── costPerKm
 ├── fixedCost
 ├── availableFrom
 └── availableTo
```

У майбутньому можна додати:

- температурний режим;
- тип кузова;
- обмеження по категоріях;
- максимальну кількість точок;
- доступність водія.

---

# 14. Рейс

Рейс повинен бути окремою сутністю.

```text
Shipment Trip
 ├── Vehicle
 ├── Origin
 ├── Stops
 ├── Cargo
 ├── Departure
 ├── Expected Arrival
 ├── Distance
 ├── Cost
 └── Status
```

Статуси:

```text
PLANNED
READY
IN_TRANSIT
DELIVERED
CANCELLED
```

---

# 15. Вантаж

Вантаж повинен бути відокремлений від самого рейсу.

Один рейс може перевозити декілька вантажів:

```text
Trip #102

Store A → Store C
Product X × 20

Store A → Store D
Product Y × 15

Store B → Store D
Product Z × 30
```

Це дозволяє реалізувати консолідацію.

---

# 16. Консолідація вантажів

Перед створенням нового рейсу система повинна перевіряти:

```text
Чи існує рейс
    ↓
Чи збігається напрямок
    ↓
Чи є достатня місткість
    ↓
Чи вкладається доставка в time window
    ↓
Чи вигідніше об'єднати
    ↓
Так → додати вантаж
Ні → створити новий рейс
```

---

# 17. Оптимізація завантаження

Потрібно враховувати не лише вагу.

Автомобіль може бути обмежений:

- вагою;
- об'ємом;
- кількістю палет;
- кількістю місць;
- типом вантажу.

Тому в майбутньому задача може перейти до моделі:

```text
Vehicle Routing Problem
+
Vehicle Capacity Problem
+
Time Windows
+
Inventory Constraints
```

Для MVP достатньо реалізувати спрощену модель.

---

# 18. MVP логістики

Перший етап не повинен намагатися вирішити повну задачу оптимізації маршрутів.

MVP:

### Inventory

- залишки;
- мінімальний запас;
- резерв;
- доступний для переміщення запас.

### Transfer Request

- source store;
- destination store;
- product;
- quantity;
- priority;
- deadline.

### Trip

- vehicle;
- origin;
- destination;
- cargo;
- status.

### Basic Optimization

Система повинна:

1. знайти магазини з доступним надлишком;
2. визначити найкраще джерело;
3. сформувати переміщення;
4. знайти існуючий сумісний рейс;
5. спробувати додати вантаж;
6. якщо це недоцільно — створити новий рейс.

# 27. Майбутній алгоритм оптимізації

Алгоритм повинен працювати приблизно так:

```text
1. Отримати всі актуальні потреби
        ↓
2. Визначити критичні потреби
        ↓
3. Знайти доступні джерела
        ↓
4. Перевірити safety stock
        ↓
5. Побудувати можливі переміщення
        ↓
6. Знайти існуючі рейси
        ↓
7. Перевірити можливість консолідації
        ↓
8. Розрахувати вартість варіантів
        ↓
9. Врахувати час очікування
        ↓
10. Врахувати ризик дефіциту
        ↓
11. Вибрати найкращий варіант
        ↓
12. Створити / оновити рейс
```

# 29. Архітектурний принцип

SupplyVector не повинен перетворюватися на систему, де вся бізнес-логіка знаходиться у React-компонентах.

Правило:

```text
UI
 ↓
Feature API / Hooks
 ↓
Service
 ↓
Query
 ↓
Database
```

Компоненти відповідають за відображення та взаємодію.

Сервіси відповідають за бізнес-правила.

SQL відповідає за отримання та зміну даних.

---

# 30. Головний принцип SupplyVector

SupplyVector повинен відповідати не на питання:

> «Як заповнити машину на 100%?»

А на питання:

> «Як перевезти необхідний товар найефективніше, не допускаючи критичного дефіциту та зайвих витрат?»

Тому оптимальна машина може бути:

- повною;
- частково завантаженою;
- відправленою негайно;
- відправленою пізніше;
- об'єднаною з іншим переміщенням.

Рішення повинно прийматися на основі **сукупної вартості логістичного рішення**, а не одного показника.

# 32. Мета проєкту

SupplyVector розвивається від простої системи обліку запасів у бік повноцінної системи **управління розподіленою мережею запасів та логістичними потоками**.

Ключова модель:

```text
             ┌─────────────┐
             │   Store A   │
             │   Stock     │
             └──────┬──────┘
                    │
                    │
        ┌───────────┼───────────┐
        │           │           │
        ▼           ▼           ▼
   ┌────────┐  ┌────────┐  ┌────────┐
   │Store B │  │Store C │  │Store D │
   │ Stock  │  │ Stock  │  │ Stock  │
   └────────┘  └────────┘  └────────┘
        │           │           │
        └───────────┼───────────┘
                    ▼
             ┌─────────────┐
             │  Logistics  │
             │ Optimization│
             └─────────────┘
```

Мережа не залежить від одного центрального складу.

Кожен магазин потенційно є частиною логістичної мережі.

Система повинна постійно знаходити баланс між:

```text
Availability
      +
Transport Efficiency
      +
Delivery Time
      +
Inventory Safety
      +
Cost
```

Саме цей баланс є основою логіки SupplyVector.
