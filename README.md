# SupplyVector

SupplyVector — система управління розподіленою складською та транспортною логістикою торговельної мережі.

Система використовує магазини мережі не лише як торгові точки, а і як розподілені складські вузли. Товар переміщується між цими вузлами залежно від потреби, доступного запасу, резервів, транспортних можливостей, відстані, часу очікування та пріоритету.

Система поєднує:

- облік користувачів та їхніх повноважень;
- облік магазинів і складських можливостей;
- облік товарів та запасів;
- формування заявок на переміщення товарів;
- резервування запасу;
- планування завантаження транспортних засобів;
- формування рейсів і маршрутів;
- контроль виконання переміщень;
- аналітику та аудит;
- автоматизовані рекомендації щодо формування рейсів;
- ручне рішення відповідальної особи про відправлення транспорту.

---

## 1. Основна концепція

SupplyVector працює як система керування розподіленою мережею складських вузлів.

Кожен магазин мережі може виконувати одну або обидві функції:

1. **Торгова точка** — місце продажу товарів.
2. **Складський вузол** — джерело або отримувач товару для внутрішніх переміщень.

Окремий логістичний центр не є обов'язковою частиною мережі.

Система визначає:

- де є доступний товар;
- де існує потреба;
- який товар може бути переміщений;
- який запас уже зарезервований;
- які транспортні засоби доступні;
- які переміщення доцільно об'єднати;
- коли доцільно сформувати рейс;
- які переміщення мають вищий пріоритет.

Рішення про фактичне відправлення транспортного засобу може прийматися автоматичною рекомендацією системи або відповідальною людиною вручну.

---

# 2. Основні принципи системи

## 2.1. Розподілений склад

Запас товару фізично знаходиться у різних магазинах мережі.

Кожен магазин має власний залишок товарів і може мати складську місткість.

## 2.2. Доступний запас

Для логістичних операцій система розрізняє:

- фізичний запас;
- зарезервований запас;
- доступний для переміщення запас.

Доступний запас не включає кількість, яка вже зарезервована для інших операцій.

## 2.3. Резервування

Резервування запасу виконується атомарно на рівні PostgreSQL.

Для критичних операцій використовується принцип:

```sql
UPDATE inventory
SET reserved = reserved + $quantity
WHERE store_id = $storeId
  AND product_id = $productId
  AND quantity - reserved >= $quantity
RETURNING *;
```

Операція одночасно перевіряє доступність запасу та виконує його резервування.

Система не покладається на послідовність:

```text
SELECT available
→ перевірка
→ UPDATE
```

для критичних резервувань, оскільки паралельні запити можуть створити race condition.

# 3. Користувачі та повноваження

Користувачі системи мають різні ролі та повноваження.

Поточна роль користувача визначає:

- які користувачі доступні для перегляду;
- які користувачі можуть створюватися;
- які ролі можна призначати;
- які логістичні операції доступні;
- які магазини доступні;
- які операції можуть бути підтверджені або змінені.

Повноваження реалізуються через централізовану систему:

```text
lib/auth/permissions.ts
lib/auth/policies.ts
```

Логістичні permissions підключаються до тієї самої системи.

Наприклад:

```text
logistics:read
logistics:create
logistics:update
logistics:approve
logistics:dispatch
logistics:cancel
logistics:manage
```

Фактичний перелік permissions визначається реалізацією системи.

Перевірка прав виконується не лише на UI-рівні.

Критичні операції перевіряють permissions/policies на сервері.

# 4. Магазини

Кожен магазин містить:

- назву;
- місто;
- адресу;
- координати;
- активність;
- складську місткість;
- логістичні характеристики.

Магазин може бути:

- джерелом товару;
- отримувачем товару;
- проміжною точкою маршруту;
- складським вузлом.

---

# 5. Товари

Товар має:

- назву;
- SKU;
- категорію;
- статус;
- логістичні характеристики.

Логістичні характеристики можуть включати:

- вагу;
- об'єм;
- габарити;
- одиницю вимірювання;
- кількість одиниць у транспортній упаковці.

Ці параметри використовуються під час планування завантаження транспорту.

---

# 6. Запаси

Для кожної пари:

```text
магазин + товар
```

система зберігає запас.

Основні значення:

```text
quantity
reserved
available
min_stock
```

Доступний запас визначається як:

```text
available = quantity - reserved
```

Запас нижче мінімального рівня може створювати потребу в поповненні.

---

# 7. Потреба в товарі

Потреба виникає, коли магазину необхідна додаткова кількість товару.

Основними причинами є:

- низький залишок;
- прогнозований дефіцит;
- запланований попит;
- ручна заявка;
- операційна потреба.

Потреба не означає автоматичне негайне відправлення автомобіля.

Вона стає основою для формування `transfer_request`.

---

# 8. Transfer Request

`transfer_request` описує потребу перемістити товар між двома складськими вузлами.

Заявка містить:

- товар;
- кількість;
- магазин-отримувач;
- потенційне джерело;
- пріоритет;
- статус;
- дату створення;
- крайній допустимий час очікування;
- додаткові логістичні параметри.

Життєвий цикл заявки:

```text
created
→ planned
→ reserved
→ assigned
→ scheduled
→ in_transit
→ delivered
```

Можливі альтернативні стани:

```text
cancelled
rejected
expired
```

---

# 9. Пріоритети

Кожне переміщення отримує пріоритет.

Пріоритет враховує:

- критичність дефіциту;
- поточний запас;
- мінімальний запас;
- час до очікуваного дефіциту;
- час існування заявки;
- бізнес-критичність товару;
- інші операційні параметри.

Пріоритет використовується для:

- сортування заявок;
- формування кандидатів на рейс;
- прийняття рішення про відправлення.

---

# 10. Джерело товару

Для заявки система визначає доступні магазини-джерела.

Джерело повинно:

- мати доступний запас;
- мати достатню кількість товару;
- не порушувати власний мінімальний запас;
- бути доступним для логістичного переміщення.

Якщо товар доступний у декількох магазинах, джерела порівнюються за логістичними параметрами.

---

# 11. Резервування запасу

Після вибору джерела необхідна кількість товару резервується.

Резервування:

- виконується атомарно;
- прив'язується до `transfer_request`;
- не дозволяє двом паралельним заявкам використати один і той самий доступний запас;
- може бути скасоване при скасуванні заявки;
- звільняється після завершення або скасування відповідної операції.

Для цього використовується окрема сутність:

```text
inventory_reservations
```

---

# 12. Транспорт

Система містить інформацію про транспортні засоби.

Основні характеристики:

```text
vehicle
- id
- name
- registration_number
- capacity_weight
- capacity_volume
- status
```

Стани транспортного засобу можуть включати:

```text
available
reserved
in_trip
maintenance
inactive
```

Транспорт має обмеження за:

- вагою;
- об'ємом;
- кількістю вантажних місць;
- іншими характеристиками.

---

# 13. Завантаження автомобіля

Система не намагається сформувати абсолютно повну машину за будь-яку ціну.

Основний принцип:

> Машина не їде порожняком, але очікування додаткового вантажу не повинно бути безмежним.

Тому при формуванні рейсу враховуються:

- поточне завантаження;
- доступні заявки;
- пріоритет заявок;
- відстань;
- сумісність напрямків;
- максимальний час очікування;
- місткість автомобіля.

---

# 14. Консолідація вантажу

Система об'єднує сумісні переміщення в один рейс.

Наприклад:

```text
Магазин A
  ↓
Магазин B
Магазин C
Магазин D
```

можуть бути об'єднані в один маршрут, якщо:

- транспорт має достатню місткість;
- переміщення сумісні;
- час очікування не перевищує допустимий;
- маршрут залишається логістично доцільним.

---

# 15. Max Wait Timer

Для заявок, які очікують консолідації, використовується максимальний час очікування.

Після досягнення `max_wait` заявка більше не очікує накопичення додаткового вантажу за звичайними правилами.

Вона переходить у стан, де система рекомендує сформувати рейс.

Це запобігає ситуації:

```text
низьке завантаження
→ очікування
→ очікування
→ очікування
→ місяці очікування
```

---

# 16. Формування рейсу

Рейс (`trip`) об'єднує:

- транспорт;
- водія або відповідального;
- одну або декілька заявок;
- маршрут;
- точки зупинок;
- вантаж.

Основні сутності:

```text
trips
trip_stops
trip_items
```

---

# 17. Маршрут

Маршрут складається з послідовності точок.

Наприклад:

```text
Warehouse A
    ↓
Store B
    ↓
Store C
    ↓
Store D
```

Для MVP використовується географічна відстань між координатами.

Відстань може розраховуватися за формулою Haversine.

Реальний дорожній час не є частиною базового MVP.

Інтеграція з OSRM, Google Maps або іншим routing API є окремим напрямком розвитку.

---

# 18. Евристика формування рейсів

Перший алгоритм планування є евристичним.

Система не виконує повну глобальну оптимізацію VRP.

Базовий алгоритм:

1. отримати активні `transfer_requests`;
2. відсортувати їх за пріоритетом;
3. визначити доступні джерела;
4. визначити найближчі доцільні джерела;
5. перевірити доступний запас;
6. перевірити місткість транспорту;
7. знайти сумісні заявки;
8. сформувати кандидатний рейс;
9. застосувати `max_wait`;
10. сформувати рекомендацію щодо відправлення.

Поточна евристика є основою для подальшого розвитку алгоритму.

# 19. Рішення про відправлення

Система розділяє:

```text
recommendation
```

і

```text
decision
```

Алгоритм може рекомендувати:

```text
Dispatch recommended
```

але остаточне рішення може прийняти відповідальна людина.

Людина може:

- підтвердити рейс;
- відкласти рейс;
- змінити склад вантажу;
- змінити транспорт;
- скасувати рейс.

Ручне рішення зберігається в системі та потрапляє до аудиту.

`trip_items` визначає вантаж рейсу.

Запис містить:

- товар;

- джерело;
- отримувача;

# 23. Місткість складських вузлів

Магазини можуть мати обмежену складську місткість.

Для цього використовується:


Місткість може контролюватися за:

- об'ємом;
- вагою;
- кількістю палетомісць;
- іншими логістичними параметрами.

Система враховує складську місткість при плануванні поставок.

- доступний запас;
- дефіцит;

- зміну ролей;
- зміну статусів;
- створення transfer request;
- резервування;
- зміну рейсу;
- підтвердження рейсу;
- ручне відправлення;
- скасування;
- інші критичні логістичні дії.

Audit record містить:

- користувача;
- action;
- entity;
- entityId;
- timestamp;
- meta.

# 30. Auth architecture

Поточний користувач визначається на сервері.

```text
app/layout.tsx
    ↓
getCurrentUser()
    ↓
AppProviders
    ↓
AuthProvider
    ↓
useAuth()
```

`AuthProvider` отримує `initialUser`.

Клієнтські компоненти використовують:

```ts
useAuth();
```

для доступу до поточного користувача.

Server-side код використовує серверні auth-функції.

Сесія використовує cookies.

# 32. Пагінація

Великі колекції використовують серверну пагінацію.

API використовує:

```text
?page=1&limit=20
```

Стандартний розмір сторінки:

```text
20
```

API повертає:

```text
{
  users: [],
  page: 1,
  limit: 20,
  total: 100,
  totalPages: 5
}
```

Пагінація застосовується до користувачів та інших великих колекцій.

---

# 33. База даних

Основна СУБД:

```text
PostgreSQL
```

Підключення:

```text
@neondatabase/serverless
```

Система використовує SQL-запити через Neon.

Критичні операції, що потребують атомарності, реалізуються SQL-операціями, які виконують перевірку та зміну стану в одному запиті.

---

# 34. Міграції

Схема бази даних версіонується через нумеровані SQL-міграції.

Структура:

```text
db/
  migrations/
    001_init.sql
    002_add_users.sql
    003_add_inventory.sql
    004_add_transfer_requests.sql
    005_add_logistics.sql
```

Кожна зміна структури БД створює нову міграцію.

`schema.sql` не використовується як єдиний механізм історії змін.

Міграції є частиною репозиторію та відповідають конкретній версії застосунку.

# 35. Seed data

Seed-дані використовуються для локального розвитку та тестування.

Seed не є механізмом міграції.

Структурні зміни виконуються через migrations.

# 39. Принципи розвитку алгоритму

Алгоритм логістики розвивається поступово.

Перший рівень:

```text
priority
+
nearest source
+
available inventory
+
vehicle capacity
+
max wait
```

Наступний рівень додає:

- складнішу консолідацію;
- декілька джерел;
- складніші маршрути;
- часові вікна;
- транспортні обмеження;
- оцінку вартості.

Після накопичення реальних даних система може перейти до складніших моделей оптимізації маршрутів.

Повна VRP-оптимізація не є базовою вимогою першої реалізації.

# 40. Ручне керування

Автоматична логіка не забирає рішення у відповідальної особи.

Система може показати:

```text
Recommended trip
```

разом із:

- завантаженням;
- заявками;
- маршрутом;
- джерелами;
- отримувачами;
- пріоритетами;
- очікуванням;
- використаною місткістю.

Користувач із відповідним permission приймає рішення:

```text
Approve
```

або:

```text
Modify
```

або:

```text
Reject
```

Ручна дія зберігається в аудиті.

# 41. Основна бізнес-логіка

SupplyVector керує не окремими доставками, а потоком товару між розподіленими складськими вузлами.

Система постійно порівнює:

```text
де є товар
vs
де він потрібен
```

та:

```text
потреба
vs
транспорт
```

і:

```text
вартість очікування
vs
вартість відправлення
```

Рішення формується з урахуванням пріоритету, доступного запасу, резервів, транспортної місткості, відстані та часу очікування.

Остаточне рішення про відправлення може залишатися за людиною.

# 44. Правило для бізнес-логіки

Бізнес-правила не дублюються у React-компонентах.

UI відображає доступні користувачу операції.

Сервер визначає, чи має користувач право виконувати операцію.

Service layer визначає бізнес-логіку.

Query layer працює з базою.

Це дозволяє зберігати однакову поведінку незалежно від того, звідки викликана операція.

# 45. Правило критичних операцій

До критичних належать:

- зміна ролі;
- деактивація користувача;
- резервування запасу;
- звільнення резерву;
- створення рейсу;
- підтвердження рейсу;
- відправлення транспорту;
- скасування рейсу;
- зміна кількості товару;
- завершення переміщення.

Критичні операції:

1. перевіряють permissions;
2. виконують бізнес-перевірки;
3. змінюють БД;
4. створюють audit record.

# 46. Фінальна модель системи

SupplyVector є системою керування товарним потоком у мережі розподілених складських вузлів.

```text
                   ┌───────────────┐
                   │   Inventory   │
                   └───────┬───────┘
                           │
                           ▼
                   ┌───────────────┐
                   │ Transfer      │
                   │ Request       │
                   └───────┬───────┘
                           │
                           ▼
                   ┌───────────────┐
                   │ Reservation   │
                   └───────┬───────┘
                           │
                           ▼
                   ┌───────────────┐
                   │ Consolidation │
                   └───────┬───────┘
                           │
                           ▼
                   ┌───────────────┐
                   │ Trip          │
                   │ Recommendation│
                   └───────┬───────┘
                           │
                    Human decision
                           │
                           ▼
                   ┌───────────────┐
                   │ Dispatch      │
                   └───────┬───────┘
                           │
                           ▼
                   ┌───────────────┐
                   │ Delivery      │
                   └───────┬───────┘
                           │
                           ▼
                   ┌───────────────┐
                   │ Inventory     │
                   │ Update        │
                   └───────────────┘
```

Система поєднує запаси, потребу, резервування, транспорт і прийняття логістичних рішень в одному керованому процесі.

# NETWORK

## `stores`

Магазини мережі та вузли розподіленого зберігання.

| Field             | Type      | Description                                |
| ----------------- | --------- | ------------------------------------------ |
| `id`              | UUID      | Ідентифікатор магазину                     |
| `name`            | TEXT      | Назва                                      |
| `city`            | TEXT      | Місто                                      |
| `address`         | TEXT      | Адреса                                     |
| `is_storage_node` | BOOLEAN   | Участь магазину в розподіленому зберіганні |
| `max_capacity`    | NUMERIC   | Максимальна місткість запасу               |
| `latitude`        | NUMERIC   | Географічна широта                         |
| `longitude`       | NUMERIC   | Географічна довгота                        |
| `created_by`      | UUID      | Користувач, який створив запис             |
| `updated_by`      | UUID      | Користувач, який оновив запис              |
| `created_at`      | TIMESTAMP | Час створення                              |
| `updated_at`      | TIMESTAMP | Час оновлення                              |

Комбінація:

```text
(name, city, address)
```

є унікальною.

`is_storage_node` визначає, чи бере магазин участь у розподіленому зберіганні та вихідних переміщеннях запасів.

`max_capacity = NULL` означає відсутність заданого обмеження місткості.

Координати обмежені:

```text
latitude:  -90 ... 90
longitude: -180 ... 180
```

## `logistics_routes`

Відстані та характеристики маршрутів між магазинами.

| Field                        | Type      | Description            |
| ---------------------------- | --------- | ---------------------- |
| `id`                         | UUID      | Ідентифікатор маршруту |
| `store_a_id`                 | UUID      | Перший магазин         |
| `store_b_id`                 | UUID      | Другий магазин         |
| `distance_km`                | NUMERIC   | Відстань у кілометрах  |
| `estimated_duration_minutes` | INTEGER   | Орієнтовна тривалість  |
| `is_active`                  | BOOLEAN   | Статус маршруту        |
| `created_at`                 | TIMESTAMP | Час створення          |
| `updated_at`                 | TIMESTAMP | Час оновлення          |

Для пари магазинів використовується один запис.

Унікальність забезпечується:

```text
(store_a_id, store_b_id)
```

та правилом:

```text
store_a_id < store_b_id
```

Це дозволяє зберігати маршрут між двома магазинами один раз незалежно від напрямку переміщення.

# INVENTORY

## `inventory`

Поточний залишок конкретного товару в конкретному магазині.

| Field               | Type      | Description                 |
| ------------------- | --------- | --------------------------- |
| `id`                | UUID      | Ідентифікатор               |
| `store_id`          | UUID      | Магазин                     |
| `product_id`        | UUID      | Товар                       |
| `quantity`          | INTEGER   | Фактичний залишок           |
| `reserved_quantity` | INTEGER   | Зарезервована кількість     |
| `min_stock`         | INTEGER   | Мінімальний запас           |
| `max_stock`         | INTEGER   | Максимальний цільовий запас |
| `created_at`        | TIMESTAMP | Час створення               |
| `updated_at`        | TIMESTAMP | Час оновлення               |

Комбінація:

```text
(store_id, product_id)
```

є унікальною.

Основні обмеження:

```text
quantity >= 0
reserved_quantity >= 0
reserved_quantity <= quantity
min_stock >= 0
max_stock IS NULL OR max_stock >= min_stock
```

Доступний для переміщення запас визначається з урахуванням активного резервування.

# VIEWS

## `v_trip_utilization`

Представлення для контролю завантаження транспортних засобів.

Представлення об'єднує:

```text
trips
  ↓
vehicles
  ↓
trip_items
  ↓
transfer_requests
  ↓
products
```

і розраховує:

| Field                    | Description                              |
| ------------------------ | ---------------------------------------- |
| `trip_id`                | Поїздка                                  |
| `status`                 | Статус                                   |
| `vehicle_id`             | Транспорт                                |
| `vehicle_name`           | Назва транспорту                         |
| `capacity_weight`        | Вантажопідйомність                       |
| `capacity_volume`        | Максимальний об'єм                       |
| `loaded_weight_kg`       | Фактична вага вантажу                    |
| `loaded_volume_m3`       | Фактичний об'єм вантажу                  |
| `weight_utilization_pct` | Відсоток використання вантажопідйомності |
| `volume_utilization_pct` | Відсоток використання об'єму             |

Вага вантажу розраховується як:

```text
quantity × product.weight_kg
```

Об'єм вантажу розраховується як:

```text
quantity × product.volume_m3
```

Якщо транспортний засіб не має заданої `capacity_volume`, відсоток використання об'єму залишається `NULL`.

# Data Integrity

База даних контролює ключові правила цілісності даних через `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE` та `CHECK` constraints.

Основні правила:

- користувач має унікальний email;
- роль має унікальний код;
- SKU товару є унікальним;
- комбінація назви, міста та адреси магазину є унікальною;
- один товар має один запис запасу в конкретному магазині;
- кількість запасу не може бути від'ємною;
- зарезервований запас не може перевищувати фактичний;
- максимальний запас не може бути меншим за мінімальний;
- магазин-джерело та магазин-призначення не можуть збігатися;
- кількість товару у переміщенні та вантажі повинна бути більшою за нуль;
- координати магазинів перевіряються на допустимий географічний діапазон;
- вантажопідйомність транспортного засобу повинна бути більшою за нуль;
- часові інтервали перевіряються на коректну послідовність;
- статуси основних сутностей обмежені визначеним набором значень;
- маршрут між двома магазинами зберігається один раз;
- ручне логістичне рішення завжди має користувача, який його прийняв;
- системне логістичне рішення не має `decided_by`.

Структура бази даних розвивається через послідовні SQL-міграції.

```text
db/
└── migrations/

    ├── 0003_transport.sql
    ├── 0004_logistics_decisions.sql
    ├── 0005_product_physical_attributes.sql
    ├── 0006_trip_utilization_view.sql
    ├── 0007_store_coordinates.sql
    └── 0008_logistics_decision_source.sql
```

### Migration 0001 — Initial Schema

Створює базові домени:

```text
users
roles
user_roles
sessions
password_resets
password_history
audit_logs

stores
user_stores

products

inventory

shipments
shipment_items

inventory_movements
```

Також створює необхідні foreign keys, indexes, unique constraints та check constraints.

Міграція оновлює роль `viewer` до `operator`.

Додає:

```text

inventory.max_stock

```

Також додає індекси для роботи із запитами на переміщення та активними резервуваннями.

### Migration 0003 — Transport

Створює:

```text

```

для планування транспортних поїздок та консолідації вантажів.

Створює:

```text

```

для роботи з маршрутами та рішеннями щодо виконання переміщень.

Додає до `products`:
